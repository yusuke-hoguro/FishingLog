# Linux VM再起動機能 設計書

## 1. 目的と対象範囲

Aアプリからの要求を受けて、BアプリがCアプリにLinux VMの再起動を依頼し、利用可能状態への復帰を確認して結果をAアプリへ返す。

本機能の対象は、稼働中のLinux VMの再起動とする。停止中のLinux VMを起動する機能は含めない。

## 2. 構成

| 要素 | 配置・役割 |
| --- | --- |
| Aアプリ | 再起動要求をBアプリへ送り、処理結果を表示するフロントエンド |
| Bアプリ | Ubuntu VM上で動作し、Cアプリへの再起動要求、TCP切断、再接続監視、結果返却を行う |
| Cアプリ | 対象のLinux VM上で動作し、再起動要求へのACK返却後にLinux VMのrebootを実行する |
| Linux VM | 再起動対象。再起動後にCアプリが通信可能な状態へ復帰する |
| QNX | Linux VMのホスト環境。本機能からSSH接続やVM状態の直接取得は行わない |

```text
Aアプリ
  │ 再起動要求／結果
  ▼
Bアプリ（Ubuntu VM）
  │ TCP通信
  ▼
Cアプリ（再起動対象のLinux VM）
  │ reboot
  ▼
Linux VMの再起動
```

## 3. 前提

- 再起動要求時点でLinux VMが稼働し、BアプリからCアプリへTCP接続できること。
- CアプリがLinux VMのrebootを実行できる権限を持つこと。
- Linux VMの再起動後、Cアプリが起動し、Bアプリから再接続できること。
- Bアプリは対象のLinux VMの再起動中も動作を継続できること。
- QNXへSSH接続しない。QNXの操作や状態取得に必要な認証情報を本機能のために保持しない。

## 4. 再起動要求フロー

```text
Aアプリ → Bアプリ：再起動要求
Bアプリ → Cアプリ：TCPで再起動要求
Cアプリ → Bアプリ：ACK（要求受付済み）
Bアプリ：ACK受信後、TCP接続を切断
Cアプリ：Linux VMのrebootを実行
Bアプリ：一定間隔でCアプリへのTCP再接続を試行
  ├─ 期限内に復帰確認成功 → AアプリへOK
  └─ タイムアウト         → AアプリへNG
```

1. AアプリはBアプリへ再起動を要求する。
2. BアプリはTCP通信でCアプリへ再起動を要求する。
3. Cアプリは要求を受け付け、BアプリへACKを返す。ACKは受付完了を示し、再起動完了を示すものではない。
4. BアプリはACKを受信した後、CアプリとのTCP接続を切断する。
5. Cアプリは、ACK返却およびBアプリによるTCP切断の後にLinux VMのrebootを実行する。
6. Bアプリは設定された再接続間隔でCアプリへのTCP再接続を繰り返す。
7. Bアプリは期限内に復帰を確認できた場合、AアプリへOKを返す。期限内に確認できなかった場合はNGを返す。

ACK受信とTCP切断、reboot実行の順序を保つ。再起動開始前のCアプリに再接続しただけで、再起動完了と誤判定しないようにする。

## 5. 利用可能状態と成功判定

Linux VMの状態はQNXから直接取得せず、Bアプリから見たCアプリの接続可否を基準に利用可能状態を判定する。

| Bアプリから見た状態 | 判定 |
| --- | --- |
| CアプリへTCP接続できない | 利用可能状態を確認できない |
| CアプリへTCP再接続できる | 通信の復帰を確認できる |
| TCP再接続後にCアプリから正常応答を取得できる | アプリケーションとしての利用可能状態を確認できる |

TCP再接続後は、可能であればCアプリから正常応答が返るところまで確認して成功とする。正常応答の確認を組み込む場合は、その確認までを復帰待ちのタイムアウト内で行う。

接続不可だけでは、Linux VMの停止、再起動中、通信障害、Cアプリの停止を区別できない。Aアプリへ返すNGは、期限内に利用可能状態への復帰を確認できなかったことを示し、Linux VMの停止やrebootの失敗を断定するものではない。

## 6. 初期実装と将来の拡張

初期実装は同期方式とする。BアプリはAアプリからの要求を受けて再起動処理と復帰確認を行い、処理結果が確定してから同じ要求への応答としてOKまたはNGを返す。

再起動要求、ACK受信、TCP切断、再接続ループ、復帰判定を、Bアプリ内の独立したサービスまたはユースケースとして切り出す。HTTPの要求・応答処理とは分離し、後から非同期方式へ改良できる構成にする。

非同期方式への改良時は、この再起動処理をバックグラウンドで実行し、Aアプリには受付結果を先に返す。その後、Aアプリが状態確認APIを定期的に呼び出して処理結果を取得する構成へ拡張する。

## 7. タイムアウトと再接続間隔

- 復帰待ちのタイムアウトと再接続間隔は、実環境でのLinux VMの再起動時間およびCアプリの起動時間を実測して決める。
- 再接続ループには上限時間を設け、無期限に待ち続けない。
- 各TCP接続試行と、実装する場合の正常応答確認にも待ち時間の上限を設け、復帰待ち全体の期限を超えないようにする。
- 同期方式では、Aアプリ、Bアプリおよび通信経路のHTTPタイムアウトと整合させ、再起動処理の結果を返却できる待ち時間を確保する。
- 固定の秒数は本設計では定めず、実測結果に基づき設定値として管理する。

## 8. 制約

- Linux VMが停止中の場合はCアプリへ到達できないため、本方式ではLinux VMを起動できない。
- Linux VMが稼働中でも、Cアプリが停止している場合や通信できない場合は、Cアプリ経由の再起動要求を実行できない。
- 本機能はQNXへSSH接続せず、QNXからLinux VMの状態を直接取得しないため、VM自体の状態を確定する機能は持たない。
- 同期方式では再起動と復帰確認が完了するまでAアプリが応答を待つ。実測した所要時間とHTTPタイムアウトを踏まえ、必要に応じて非同期方式へ改良する。

## 9. Aアプリ（LEAP）のフロントエンド仕様

本節では、AアプリをLEAPとし、フロントエンドとバックエンドを区別して記載する。Aアプリのフロントエンドは、Aアプリのバックエンドを経由してBアプリへ再起動を要求し、処理結果を受け取る。

### 9.1. 再起動ボタンと画面動作

- Linux VMの再起動専用ボタンを設ける。
- ボタン押下直後にボタンを`disabled`にし、二重押下を防止する。
- 処理中は「再起動中...」等を表示する。
- Bアプリから再起動完了のOK/NGレスポンスがAアプリのバックエンドを経由して返るまで、ボタンは再押下不可とする。
- OK受信時は、ボタンの`disabled`を解除して通常表示へ戻す。
- NG受信時も、ボタンの`disabled`を解除して通常表示へ戻し、エラーを表示する。
- 再起動処理中も、他の画面操作は可能とする。

### 9.2. 同期リクエスト・レスポンスの流れ

```text
Aアプリ（LEAP）フロントエンド：再起動ボタン押下、disabled化、処理中表示
  ↓ 再起動要求
Aアプリ（LEAP）バックエンド
  ↓ 再起動要求
Bアプリ
  ↓ TCPで再起動要求
Cアプリ
  ↓ BアプリへACKを返却し、BアプリがTCP接続を切断
Linux VM：Cアプリがrebootを実行
  ↓
Bアプリ：一定間隔でCアプリへのTCP再接続を試行し、復帰を確認
  ├─ 期限内に再接続・復帰確認成功 → OK
  └─ タイムアウト                 → NG
  ↓ OK/NGレスポンス
Aアプリ（LEAP）バックエンド
  ↓ 結果返却
Aアプリ（LEAP）フロントエンド：通常表示へ戻し、再押下可能にする。NG時はエラー表示
```

Bアプリは第4節・第5節に従って再起動後の復帰を判定し、結果が確定してから同じ要求への応答としてOK/NGを返す。Aアプリのバックエンドは、その結果をフロントエンドへ返却する。CアプリのACKは受付完了であり、この時点ではボタンを再押下可能にしない。

同期方式は再起動処理の結果を同じ要求への応答で返すことを指す。フロントエンドは応答待ちの間も他の画面操作を受け付ける。
